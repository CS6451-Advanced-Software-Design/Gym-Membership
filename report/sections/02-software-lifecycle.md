## Our Lifecycle

In our Gym Membership Project, every change went through each member's branch which then was sent as pull request, on every pull request the CI checks were performed after that only, it got merged into the main branch. From 25 Oct, the main was protected so that nothing goes without a Pull request. The CI Checks we included were unit tests, integration tests and end-to-end tests, ArchUnit, JaCoCo, PMD, and a metrics comment on each PR. Every merge deployed the app to Railway and rebuilt the report PDF. We had 168 merged PRs and 416 commits on main, plus Dependabot keeping the libraries updated.

We started from week 3 (21–27 Sep), one of our team members Chirag (Architect, Designer) created the project documents like role proposal and also created the first draft of requirements. Each member's GitHub handle was added to the project docs between 23 and 27 Sep.

In week 4 (28 Sep–4 Oct), we chose what to build. We did a team meeting in which each team member suggested their ideas and we all agreed on Gym membership System. On 30 Sep, the tech stack was decided and agreed upon, we chose Java with Spring Boot. The team members also chose to stay on Monolith, that is, one app, using "Package by layer". But, our Iteration 0 which was analysis and architecture was due for 4 Oct, we were running late acc. to diary created.

In Week 5 (5–11 Oct), we performed the design and roles part, in this week the roles were assigned, Chirag Aggarwal as Architect, Designer. Owns Billing and took Billing Feature, Bharat became Project Manager, Tester and took Booking Feature, Dinesh Reddy Mogili as Documentation Manager, Technical Lead + DevOps and Owns Member whereas Dhruv Punj as Business Analyst, Systems Analyst and Owns Membership Feature. The team chose the Hexagonal architecture, till that we had no feature code performed. On 7 Oct, Bharat created the repo's License (cc8c766).

In week 6 (12–18 Oct), Chirag performed quality rules, set the quality bar like CI must block bad merges, ArchUnit checks the layers, numbers must come from tools, and every pattern needs a test which merged as PR #6.

Week 7 (19–25 Oct), we built the foundation, started building features, we released our first project version: v0.1.0. We split the repo into report/ and code/. Chirag added the Spring Boot skeleton, the shared ports and a generic JSON file repository. Dhruv redrew all the diagrams and added the shared Money type and the notification and payment ports. Chirag also added Billing, with the Strategy pattern for discounts. Dhruv built Membership, with the State and Factory patterns. Bharat Reviewed the Interceptor Pattern and UC2 Book Class Sequence Diagram and went through planning how booking works for membership for his part. Dinesh Reviewed the Spring Boot skeleton and the CI pipeline as they were built and also planned the Member feature's design.

Week 8 (26 Oct–1 Nov), we built the remaining functionality, and released our project v0.2.0 version. Bharat built the Booking Features related to domain and also built two Interfaces and their Adapters. Built Booking rules in BookingService. Dinesh built the Member features with tests. Fixed CI bugs. Chirag worked on Memberships in Postman, Railway auto-deploy on merge and Architecture whereas Dhruv worked on Membership sketches, quality attributes and GUI prototypes. In the end of the week we switched to v0.3.0 version of our Project.

Week 9 (2–4 Nov) was about patterns, API and working on Report Section. Bharat worked on the Command Pattern (#128), Observer for the waitlist and Booking API with end-to-end tests. The v1.0.0 version release prepared (PR #153). Chirag got the live app and Postman up to date with Booking, All members worked on their Report Section for the completion of the Project.

## Why It Suits Us

We chose short weekly iterations with a set of week tasks so that we are on track with the project progress. We released our Project version per Iteration (v0.1.0 in Week 7, v0.2.0 in Week 8). If we run out of time, we still had something running we can showcase of our Project. We planned and designed in Weeks 3–6 before coding so that we are aligned with proper software design idea rather than fast forward coding. In a team of 4 members, there is a chance or danger of breaking each other's work while working on the Project, to resolve this we had a branch per task, where PR checks were done by CI. It catches broken tests or rule violations. Main was protected from 25 Oct. Our roles were split by features (Chirag: Billing, Bharat: Booking, Dhruv: Membership, DineshReddy: Member) which meant we rarely edited the same file. We chose Hexagonal Architecture for our project in week 5 which helped us to build our Project. We were a 4-person team so we didn't need lots of formal documents or approval steps as most of that was handled by CI, which ran the tests and the quality checks by itself. Although a teammate was still needed for reviews of PRs, the machine did the repetitive checking for us.

## Complexity vs Agility

The complexity management rules which we used in our project helped us in not letting the code become a mess, the rules we followed are - 'Hexagonal Layers' in which each feature was split into port (port.in has 19 interfaces and port.out 10 (§7 table)), service, domain and adapter, so that features did not tangle. Next we had the 'ArchUnit' (ArchitectureTest) which makes the build fail when a layer rule is broken, that failure is how it protects the design. Moreover, the 'PMD gate': PMD fails the build when it finds a design smell like GodClass, which basically stopped our PR #129, so we needed to split the BookingService into ScheduleService, AttendanceService and BookingQueries. In last we had 'Tests and coverage' which has 300 tests with around 97.3% line coverage (§8 test table). The thing that kept us fast in terms of agility was 'Small PRs', we divided our task into small progress which led us to end up with small PRs in which CI gave feedback in minutes and the Auto-deploy to Railway on every merge, so that the live app was always current. The balance we took was that the rules were automated, so they did not make us slow down much, the machine checked and we kept moving with our functionality and tasks. The place where we slipped was the late start, we had less feature code in week 5–6, as we were much in understanding and design of our project. Our Iteration 0 was due 4 Oct, in Week 4, we were also late in it. The report was also left to the end so most of the sections were still placeholders in week 8.
